title: Multi-tenant data with row-level security
description: Scope Rayfin entities per user and per organization with role-based row-level security policies and claims.sub.
---

Rayfin enforces row-level security at the API layer through `@role` policies, compiled
into Data API Builder configuration. This page covers the two shapes that come up
repeatedly: scoping rows to the signed-in user, and scoping rows to a shared organization
or team.

> [!NOTE]
> Policies compare JWT claims to fields on the *same row* — there is no join in the policy
> itself. Only three claims are available: `claims.sub` (the signed-in user's ID),
> `claims.email`, and `claims.role`. There is no built-in organization or tenant claim, so
> organization scoping is built from a stored `organization_id` field, not a claim.

## Per-user row-level security

The common case: every signed-in user can read and write only the rows they created. This
is the pattern used in [Build a todo app](/docs/recipes/todo-app):

```typescript title="rayfin/data/Todo.ts"
import { entity, role, uuid, text, boolean, date } from '@microsoft/rayfin-core';

@entity()
@role('authenticated', '*', {
  policy: (claims, item) => claims.sub.eq(item.user_id),
})
export class Todo {
  @uuid() id!: string;
  @text({ max: 100 }) title!: string;
  @boolean() isCompleted!: boolean;
  @date() createdAt!: Date;
  @text() user_id!: string;
}
```

`policy` receives the caller's `claims` and the candidate `item`; `claims.sub.eq(item.user_id)`
compiles to a DAB policy string (`@claims.sub eq @item.user_id`) that filters every read,
update, and delete, and is checked against every create.

`@anonymous()`/`@authenticated()` are shorthands for the built-in roles and accept the same
`policy` option — use whichever reads better for your entity:

```typescript
import { entity, authenticated, uuid, text } from '@microsoft/rayfin-core';

@entity()
@authenticated('*', {
  policy: (claims, item) => claims.sub.eq(item.user_id),
})
export class Todo {
  @uuid() id!: string;
  @text({ max: 100 }) title!: string;
  @text() user_id!: string;
}
```

> [!WARNING]
> `user_id` is declared `@text()`, not `@uuid()`. It isn't a foreign key to another Rayfin
> entity's primary key — it stores the caller's JWT `sub` claim, which is an opaque string
> identifier issued by the auth provider. Reserve `@uuid()` for fields that reference
> another entity's `id` through `@one()`/`@many()`.

## Per-organization row-level security

Rows shared across a team need a stored `organization_id`, plus a membership record that
says who belongs to which organization — because the policy DSL has no way to express
"the caller belongs to this row's organization" on its own.

```typescript title="rayfin/data/Organization.ts"
import { entity, role, uuid, text } from '@microsoft/rayfin-core';

@entity()
@role('authenticated', ['read', 'update', 'delete'], {
  policy: (claims, item) => claims.sub.eq(item.owner_id),
})
@role('authenticated', 'create')
export class Organization {
  @uuid() id!: string;
  @text({ max: 200 }) name!: string;
  @text() owner_id!: string;
}
```

```typescript title="rayfin/data/OrganizationMember.ts"
import { entity, role, uuid, text, one } from '@microsoft/rayfin-core';
import { Organization } from './Organization.js';

@entity()
@role('authenticated', '*', {
  policy: (claims, item) => claims.sub.eq(item.user_id),
})
export class OrganizationMember {
  @uuid() id!: string;
  @uuid() organization_id!: string;
  @one(() => Organization) organization?: Organization;
  @text() user_id!: string;
}
```

```typescript title="rayfin/data/Project.ts"
import { entity, role, uuid, text, one } from '@microsoft/rayfin-core';
import { Organization } from './Organization.js';

@entity()
@role('authenticated', '*', {
  policy: (claims, item) => claims.sub.eq(item.created_by),
})
export class Project {
  @uuid() id!: string;
  @text({ max: 200 }) name!: string;
  @uuid() organization_id!: string;
  @one(() => Organization) organization?: Organization;
  @text() created_by!: string;
}
```

Note `organization_id` is `@uuid()` here — unlike `user_id`, it *is* a foreign key: it
references `Organization.id` through `@one(() => Organization)`, so its type must match
the primary key it points at. Import `Organization` with a regular `import` (not `import
type`) — the decorator needs the runtime class value, not just its type.

The `@role` policy on `Project` above still only enforces ownership by the row's creator
(`claims.sub.eq(item.created_by)`) — Rayfin's policy DSL can't express "the caller is a
member of `item.organization_id`" directly, since that requires a join against
`OrganizationMember`. Two things layer on top of the row policy to get organization-wide
sharing:

1. **Scope every read by organization membership**, looked up first:

   ```typescript
   const memberships = await client.data.OrganizationMember.select(['organization_id'])
     .where({ user_id: { eq: session.user.id } })
     .execute();

   const projects = await client.data.Project.select(['id', 'name', 'organization_id'])
     .where({ organization_id: { eq: memberships[0].organization_id } })
     .execute();
   ```

2. **Check membership in application code before writes** — verify the caller has an
   `OrganizationMember` row for the target `organization_id` before creating or updating a
   `Project` in that organization. The row-level policy alone won't stop a member of one
   organization from writing into another's `organization_id` if your application code
   doesn't check first.

### Admin bypass with claims.role

Combine `.and()`/`.or()` to let an elevated role see or change any row, alongside the
per-owner rule:

```typescript
@role('authenticated', '*', {
  policy: (claims, item) =>
    claims.role.eq('admin').or(claims.sub.eq(item.created_by)),
})
export class Project {
  // ...
}
```

Both sides of `.or()` are parenthesized automatically, so the resulting policy is always
`(claims.role eq 'admin') or (claims.sub eq @item.created_by)` — unambiguous regardless of
operator precedence. `.and()` composes the same way, for policies that must satisfy more
than one condition at once (for example, `claims.sub.eq(item.user_id).and(item.isActive.eq(true))`).

## Best practices

- Add an explicit `@role`, `@anonymous`, or `@authenticated` decorator to every entity you
  define. An entity with none silently receives `authenticated: *` — full CRUD for any
  signed-in user, with no row-level restriction — which is rarely what you want. See
  [Data permissions](/docs/data/permissions).
- Prefer the `@anonymous()`/`@authenticated()` shorthands for the two built-in roles; use
  `@role()` directly when you need more than one role, or different rules per action.
- Include a `user_id` (or `created_by`/`owner_id`) field on every entity you scope by
  owner, and set it from the session on create — never accept it from the caller.
- Start restrictive — authenticated-only, owner-only — and widen deliberately as
  requirements grow.
